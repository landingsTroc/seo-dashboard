The finding no report had flagged

The fourteen longest guides on the site were printing \n\n at readers

The “Complete Guide (2026)” pages were pasted from Markdown without being converted. 3,789 literal \n sequences and eleven --- rules were stored as text, and WordPress wrapped each one in its own paragraph.

On /retail-technology-guide/ alone that produced 122 junk paragraphs scattered through a 4,400–word article. The same pattern ran through all fourteen. A malformed <ul> that WordPress was breaking apart was repaired in the same pass.

This appeared in no Ahrefs report, because crawlers do not grade prose. It only shows when you read the delivered HTML.

Validation before any write: plain text identical and tag count identical, on every page. For /retail-technology-guide/ that was 24,735 characters and 302 tags before and after — proof that no word was lost, joined or reflowed. A live HTML diff after the write confirmed the only change was the junk disappearing.

The correction

This replaces what I reported on 30 September and again on 14 October.

Webflow does not serve the case studies, and a Webflow seat cannot fix them

I had been reporting that these URLs were blocked on Webflow access. Having now traced how those pages are actually delivered, that was wrong in a way that matters.

  • /case-studies/* is served by WP Engine, not Webflow. The response carries WP Engine headers and none from Webflow.
  • WordPress routes the URL — an invented case study URL returns a WordPress 404.
  • But 29 of 29 pages contain no WordPress output at all: no Yoast, no wp-includes, no wp-json, and a <body> with no classes. A theme template prints an exported copy of the Webflow markup and never calls wp_head().
  • The markup is not in the database either. The post body is empty and no custom field holds it. It lives in theme files.

So editing those pages in Webflow changes nothing on the live site unless somebody re-exports the HTML and uploads it again. That is the most likely reason the same crawl report arrived three times unchanged: the work was being done somewhere that never published.

The values we need are already written, and already being discarded

Yoast holds a correct title and description for every case study. The Apple record stores “Apple Case Study | T-ROC | Retail Growth”. The page serves a 100–character title baked into the export instead. The same mismatch runs through all 34.

Which means there are two routes, and neither needs a Webflow licence:

  1. Make the template call wp_head(). Yoast takes over for all 34 at once, and the missing canonical tags and schema appear with it. This is the clean fix.
  2. Edit the exported HTML over SFTP, page by page.

Both need write access to the theme, which the SEO account does not have.

The licence question

Raised after it was noticed that the company had stopped paying for Webflow.

The pages stay up. Everything visual breaks.

Because the HTML sits on WP Engine, the URLs keep returning 200 and the text survives. But every stylesheet, script and image is loaded from the Webflow CDN — 67 unique assets, including the entire 575 KB stylesheet, three JavaScript files, the logo and roughly sixty images.

If that CDN stops answering, the 29 case studies become unstyled text with broken images.

Nothing has been withdrawn yet. All 67 assets returned 200 on 26 October, and the three Webflow projects answer “Protected page” — meaning they still exist and are still published, not “site not found”.

A lapsed hosting plan is not the same as a closed account; the second is what deletes the CDN. Worth confirming with Webflow rather than assuming. The durable fix is to copy those 67 assets onto WP Engine and rewrite the references, which ends the dependency permanently. That should happen before anything in Webflow is cancelled or deleted.

The author is declared as the organisation, not a person. These guides carry no visible byline, and inventing one would be fabricating the signal rather than recording it. The seven exclusions were left alone because declaring a link index an “article” would satisfy the crawler and misdescribe the page.

Corrected 30 October. This report first said the post template strips scripts from the body, on the evidence of /retail-staffing-services/. That was wrong, and it was a generalisation from a single case. That URL is served by page 11346, which shadows post 7874 — both hold the same slug and WordPress resolves to the page. The post’s schema never appears because its template never runs, not because anything is filtered. Four ordinary blog posts were re-measured on 30 October and every one renders its injected FAQPage correctly. No re-check of blog schema is needed; the orphaned post 7874 is a pruning candidate instead.
